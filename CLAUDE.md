# CLAUDE.md

Поведенческие рекомендации для снижения типичных ошибок LLM при написании кода. При необходимости объединяйте с инструкциями конкретного проекта.

**Компромисс:** эти рекомендации смещены в сторону осторожности, а не скорости. Для тривиальных задач руководствуйтесь здравым смыслом.

## 1. Думай, прежде чем писать код

**Не предполагай. Не скрывай непонимание. Озвучивай компромиссы.**

Перед реализацией:
- Явно формулируй свои предположения. Если не уверен — спроси.
- Если возможны несколько интерпретаций, представь их — не выбирай молча.
- Если существует более простой подход, скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно непонятно. Спроси.

## 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего «на будущее».**

- Никаких функций сверх того, что просили.
- Никаких абстракций для кода одноразового использования.
- Никакой «гибкости» или «конфигурируемости», которую не запрашивали.
- Никакой обработки ошибок для невозможных сценариев.
- Если ты написал 200 строк, а можно было 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

## 3. Хирургические изменения

**Трогай только то, что необходимо. Убирай только за собой.**

При редактировании существующего кода:
- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Следуй существующему стилю, даже если сам сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни о нём, но не удаляй.

Когда твои изменения порождают «сирот»:
- Удаляй импорты/переменные/функции, которые стали неиспользуемыми из-за ТВОИХ изменений.
- Не удаляй ранее существовавший мёртвый код, если об этом не просили.

Проверка: каждая изменённая строка должна напрямую соответствовать запросу пользователя.

## 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Итерируй до подтверждения результата.**

Превращай задачи в проверяемые цели:
- «Добавь валидацию» → «Напиши тесты для некорректных входных данных, затем добейся их прохождения»
- «Исправь баг» → «Напиши тест, воспроизводящий его, затем добейся его прохождения»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач формулируй краткий план:
```
1. [Шаг] → проверка: [критерий]
2. [Шаг] → проверка: [критерий]
3. [Шаг] → проверка: [критерий]
```

Сильные критерии успеха позволяют итерировать самостоятельно. Слабые критерии («сделай, чтобы работало») требуют постоянных уточнений.

---

**Эти рекомендации работают, если:** в диффах меньше ненужных изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы задаются до реализации, а не после ошибок.

## 5. Ключевые принципы

Извлечено из AGENTS.md, RULES.md, SOUL.md.

1. **Agent-First** — делегируй доменные задачи специализированным агентам (planner, code-reviewer, tdd-guide, security-reviewer, build-error-resolver и др.). Независимые операции запускай параллельно.
2. **Test-Driven** — тесты пишутся до реализации; критические пути обязательно проверяются.
3. **Security-First** — валидируй все входные данные, защищай секреты, сохраняй безопасные значения по умолчанию.
4. **Immutability** — всегда создавай новые объекты, никогда не мутируй существующие.
5. **Plan Before Execute** — сложные изменения разбивай на осознанные фазы до написания кода.

**Всегда:**
- Следуй устоявшимся паттернам репозитория, прежде чем изобретать новые.
- Держи изменения сфокусированными, проверяемыми и хорошо описанными.

**Никогда:**
- Не включай в вывод чувствительные данные: API-ключи, токены, секреты, абсолютные/системные пути.
- Не отправляй непротестированные изменения.
- Не обходи проверки безопасности и валидационные хуки.
- Не дублируй существующую функциональность без явной причины.

## 6. Безопасность

Извлечено из SECURITY.md, AGENTS.md.

Перед любым коммитом:
- Нет захардкоженных секретов (API-ключи, пароли, токены) — только переменные окружения или secret manager.
- Все пользовательские входные данные валидированы (schema-based, fail fast).
- Защита от SQL-инъекций (параметризованные запросы), XSS (санитизация HTML), CSRF.
- Аутентификация/авторизация проверены; rate limiting на всех endpoints.
- Сообщения об ошибках не раскрывают чувствительные данные.

При утечке секрета: немедленно ротируй его у провайдера и перепиши историю git — простого revert недостаточно.

При обнаружении проблемы безопасности: СТОП → security-reviewer → исправить CRITICAL → ротировать секреты → проверить кодовую базу на похожие проблемы.

## 7. Стиль кода

Извлечено из AGENTS.md, CLAUDE.md.

- **Иммутабельность (критично):** возвращай новые копии с изменениями, не мутируй.
- **Файлы:** много маленьких файлов лучше нескольких больших. Типично 200–400 строк, максимум 800. Организация по фичам/доменам, а не по типам.
- **Функции:** маленькие (<50 строк), без глубокой вложенности (>4 уровней) — используй ранние возвраты.
- **Ошибки:** обрабатывай явно на каждом уровне; понятные сообщения в UI, подробный контекст в логах сервера; никогда не «глотай» ошибки молча.
- **Именование:** файлы — lowercase с дефисами (`session-start.js`); переменные/функции — `camelCase`; константы — `UPPER_SNAKE_CASE`; никаких «магических чисел».

## 8. Тестирование

Извлечено из AGENTS.md, testing-правил.

- Минимальное покрытие: **80%**.
- Обязательные типы тестов: unit, integration, E2E (критические пользовательские сценарии).
- TDD-цикл: тест (RED, должен упасть) → минимальная реализация (GREEN) → рефакторинг (IMPROVE) → проверка покрытия.
- При падении тестов: проверь изоляцию тестов → проверь моки → исправляй реализацию, а не тесты (если тесты не ошибочны).
- Структура теста: Arrange–Act–Assert; имена тестов описывают проверяемое поведение.

## 9. Git и коммиты

Извлечено из git-workflow, RULES.md, CONTRIBUTING.md.

- Формат коммита: `<type>: <description>` — типы: feat, fix, refactor, docs, test, chore, perf, ci. Допустим scope: `feat(skills):`, `fix(hooks):`.
- Перед PR: проанализируй всю историю коммитов (`git diff base...HEAD`), составь развёрнутое описание с тест-планом, пуш с флагом `-u` для новой ветки.
- Перед пушем: прогони тесты локально (`npm test` / `node tests/run-all.js`) — CI гоняет то же самое.
- Изменения должны быть модульными; влияние на пользователя описывается в PR.

## 10. Архитектурные паттерны

- API response format: единый envelope (`success`, `data`, `error`, `pagination`).
- Repository pattern: инкапсуляция доступа к данным (`findAll`, `findById`, `create`, `update`, `delete`).
- Business logic зависит от абстрактного интерфейса, а не от механизма хранения.

## 11. Управление контекстом

- Избегать последних 20% окна контекста для крупных рефакторингов.
- Низкочувствительные задачи (правки, документация) терпят более высокую загрузку.
- При проблемах с билдом → build-error-resolver → фиксить поэтапно.

## 12. Документация

- Личные заметки → auto memory.
- Командные знания (архитектурные решения, API-изменения) → docs проекта.
- Если текущая задача уже создаёт документацию — не дублировать.
- Если нет очевидного места для документации — спросить перед созданием файла.

## 13. Проект

- Всё общение ведётся на русском языке.
- Технические термины и кодовые обозначения сохраняются в первоначальном виде.
- Основная рабочая директория: `./src`
- Директория для файлов с данными: `./data`
- Стек: `JavaScript`, `TypeScript`, `React`, `Redux`, `HTML/CSS`, `Node.js (module)`, `Rspack`, `pnpm`

## 14. Раскладка клавиатуры

- Если пользователь ввёл сообщение на **латинице**, но символы соответствуют клавишам **русской раскладки** — расшифруй и работай с оригинальным смыслом. Не спрашивай «что вы имели в виду?».
- Схема раскладки (одни и те же клавиши):
  ```
  Русская:  йцукенгшщзхъфывапролджэячсмитьбюё
  Английская:  qwertyuiop[]asdfghjkl;'zxcvbnm,.§
  ```
  Пример: `йцукен` → `qwerty`
  Пример: `cltkfq vjltkm gj evjkxfyb.` → `сделай модель по умолчанию`
- После расшифровки продолжи работу с расшифрованным запросом.
- Разговаривай с пользователем на русском языке, если он пишет на русском или допускает опечатки, вызванные неправильной раскладкой.

## 15. Ограничения

- Запрет на использование Python!
- Не выводи секретные поля (keys.public / keys.secret) в вывод команд, логи или консоль — этот вывод уходит через API.
